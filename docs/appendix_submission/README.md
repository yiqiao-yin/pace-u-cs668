# Final Submission

## Project Requirement

Students must build at least one project for the semester and commit their code to a GitHub repository. This is a mandatory requirement for course completion.

## Important Note

This page is for **GitHub repository submission only**. For all other course submissions (proposals, written assignments, posters, etc.), please use your school's official submission portal (e.g., Brightspace, Canvas, or as directed by your instructor).

## Grading

Students must submit their GitHub repository through the **Classes** page on your school's official portal. Your grade will be determined based on your chosen track's rubric below.

## Grading Rubrics

All students must complete the required items based on their chosen track:

- **Research Track**: Research Question, Research Design, Data Collection, Data Analysis, Paper, Poster, and GitHub Repo
- **App Track**: Research Question, App Design, Data Schema Design, App Analysis, Poster, and GitHub Repo (no paper required)

### Research Track (100 Points Total)

| Item | Requirements & Examples | Points |
|------|------------------------|--------|
| **Research Question** | Do you have a well-defined research question? <br/><br/>**10 pts (100%)**: "How can we increase rocket lifting power through fuel optimization, and what specific fuel compositions are needed to achieve the thrust-to-weight ratio required to reach Earth's upper atmosphere?" - Clear, specific, measurable, and addresses a defined problem. <br/><br/>**7 pts (70%)**: "What factors affect rocket performance and how can we improve fuel efficiency?" - Somewhat clear but lacks specific metrics or defined scope. <br/><br/>**5 pts (50%)**: "How to go to Mars?" - Too vague, no measurable outcomes, and scope is undefined. | 10 |
| **Research Design** | Is your methodology sound and well-structured? <br/><br/>**10 pts (100%)**: Clearly defines hypothesis, control variables, experimental groups, data collection methods, and statistical analysis plan. Includes detailed timeline, acknowledges limitations, and describes reproducibility measures. <br/><br/>**7 pts (70%)**: Has a general methodology but missing some components (e.g., no control group defined, or statistical methods not specified). <br/><br/>**5 pts (50%)**: Vague description like "I will collect data and analyze it" with no specific methodology or structure. | 10 |
| **Data Collection** | Is your data collection systematic and reproducible? <br/><br/>**15 pts (100%)**: Thoroughly documents all data sources with citations, detailed collection procedures with step-by-step instructions, sample size justification with power analysis, and comprehensive data validation methods. Includes complete data dictionary with variable definitions and handles missing data with documented strategy. <br/><br/>**11 pts (70%)**: Data is collected but documentation is incomplete (e.g., missing sample size rationale or unclear data cleaning procedures). Some sources documented. <br/><br/>**8 pts (50%)**: Data collection is ad-hoc with no documentation of sources or methods. Cannot be reproduced by others. | 15 |
| **Data Analysis** | Is your analysis appropriate and rigorous? <br/><br/>**15 pts (100%)**: Uses appropriate statistical methods for the research question with justification, includes comprehensive visualizations, validates all statistical assumptions with diagnostic tests, and interprets results with confidence intervals, p-values, and effect sizes. Discusses statistical power and limitations. <br/><br/>**11 pts (70%)**: Analysis is reasonable but may use suboptimal methods or lacks validation of statistical assumptions. Some visualizations included. <br/><br/>**8 pts (50%)**: Basic descriptive statistics only, or inappropriate methods for the data type (e.g., using parametric tests on non-normal data without justification). | 15 |
| **Paper** | Is your paper well-written and publication-ready? <br/><br/>**20 pts (100%)**: Follows complete academic structure (Abstract, Introduction, Literature Review, Methods, Results, Discussion, Conclusion, References). Clear, professional writing with proper citations (minimum 10-15 scholarly sources). Logical flow throughout, results fully support conclusions, and includes limitations and future work sections. <br/><br/>**14 pts (70%)**: Has all sections but some are underdeveloped. Writing is clear but may have minor organizational issues or incomplete citations (fewer than 10 sources). <br/><br/>**10 pts (50%)**: Missing sections, poor organization, or conclusions not supported by results. Minimal citations or improper formatting. | 20 |
| **Poster** | Does your poster effectively communicate your work? <br/><br/>**15 pts (100%)**: Visually appealing with professional design, clear visual hierarchy, readable from 4-6 feet distance. Includes concise problem statement, methods summary, key results with high-quality visualizations, and clear conclusions. Consistent formatting and branding throughout. <br/><br/>**11 pts (70%)**: Contains all necessary information but design is cluttered or text-heavy. Some visualizations but could be improved. Readable but not visually polished. <br/><br/>**8 pts (50%)**: Difficult to read, missing key sections, or just a wall of text. No clear visual hierarchy or poor quality images. | 15 |
| **GitHub Repo** | Is your repository well-organized and documented? <br/><br/>**15 pts (100%)**: Clear README with comprehensive project description, detailed installation instructions, usage examples with sample outputs, and thorough documentation. Well-organized folder structure (data/, src/, docs/, results/), meaningful commit history showing project progression, includes requirements.txt or environment.yml with all dependencies. Code is well-commented and follows style guidelines. <br/><br/>**11 pts (70%)**: Has README but missing some elements (e.g., no installation instructions or usage examples). Code is present but organization could be improved. Some commits but history not well-structured. <br/><br/>**8 pts (50%)**: Minimal or no README, disorganized files, no documentation. Difficult for others to understand or run the code. | 15 |

### App Track (100 Points Total)

| Item | Requirements & Examples | Points |
|------|------------------------|--------|
| **Research Question** | Do you have a well-defined problem your app solves? <br/><br/>**10 pts (100%)**: "How can we reduce food waste in college dining halls by providing students with real-time meal availability and portion tracking through a mobile app?" - Clear problem, target users, and measurable impact. <br/><br/>**7 pts (70%)**: "How can we help people waste less food?" - General direction but lacks specific user group or measurable outcomes. <br/><br/>**5 pts (50%)**: "I want to make a food app." - No clear problem statement or defined purpose. | 10 |
| **App Design** | Is your app design user-centered and well-planned? <br/><br/>**15 pts (100%)**: Includes detailed user personas with demographics and pain points, comprehensive user journey maps, high-fidelity wireframes/mockups for all screens, and thoroughly justifies each design decision. Considers accessibility (WCAG compliance), responsive design, and follows UI/UX best practices with documented style guide. <br/><br/>**11 pts (70%)**: Has wireframes or mockups but missing user research. Design is functional but may not follow best practices. Some screens documented but not comprehensive. <br/><br/>**8 pts (50%)**: No design documentation. Went straight to coding without planning the user experience. Basic sketches at best. | 15 |
| **Data Schema Design** | Is your data model well-structured and scalable? <br/><br/>**15 pts (100%)**: Clear entity-relationship diagram with all relationships documented, properly normalized tables (or justified denormalization), comprehensive schema documentation with data types, constraints, indexes, and foreign keys. Includes data dictionary, considers data growth patterns, query optimization, and backup/recovery strategy. <br/><br/>**11 pts (70%)**: Schema exists and is functional but may have redundancy issues or missing documentation. Relationships are defined but not optimized. Basic ER diagram provided. <br/><br/>**8 pts (50%)**: Ad-hoc data storage with no clear schema. Data is scattered across files or poorly structured tables. No documentation of data model. | 15 |
| **App Analysis** | Have you evaluated your app's effectiveness? <br/><br/>**15 pts (100%)**: Includes comprehensive user testing results with multiple participants, detailed performance metrics (load time, response time, memory usage), error tracking and logging implementation, user feedback analysis with actionable insights. Documents multiple iterations based on findings with before/after comparisons. <br/><br/>**11 pts (70%)**: Some testing performed but limited scope (e.g., only developer testing, no real user feedback). Basic performance awareness. One or two metrics tracked. <br/><br/>**8 pts (50%)**: No formal testing or analysis. App works but no evidence of evaluation or improvement based on data. | 15 |
| **Poster** | Does your poster effectively showcase your app? <br/><br/>**10 pts (100%)**: Shows high-quality app screenshots/demo, clearly explains problem and solution, highlights key features with visual callouts, includes detailed architecture diagram. Visually appealing, professional design with consistent branding. <br/><br/>**7 pts (70%)**: Contains app information but design is cluttered. May be missing architecture or technical details. Screenshots present but not well-organized. <br/><br/>**5 pts (50%)**: Difficult to understand what the app does. Poor quality screenshots or missing visuals. No clear value proposition. | 10 |
| **GitHub Repo** | Is your repository well-organized and deployable? Must include: 1) Frontend folder with organized components, 2) Backend folder with API structure, 3) Data engineering folder with RDS/database architecture documentation. <br/><br/>**35 pts (100%)**: Comprehensive README with detailed setup instructions for both frontend and backend, environment variables fully documented, clear folder structure separating frontend/backend/data-engineering. Meaningful commit history showing progression. Includes working demo link or complete deployment instructions (Docker, cloud). Frontend folder has organized components, assets, and routing. Backend folder has clear API routes, controllers, and middleware. Data engineering folder includes RDS architecture diagrams, migration scripts, and database setup documentation. Tests included for both frontend and backend. <br/><br/>**25 pts (70%)**: README exists with basic instructions but may be missing some environment setup or deployment steps. Has frontend and backend folders but organization could be improved. Data engineering documentation is minimal. Code works but some setup steps unclear. <br/><br/>**18 pts (50%)**: Difficult to run the app from the repository. Missing dependencies, incomplete setup instructions, or code errors. Folder structure unclear or missing required folders (frontend/backend/data-engineering). No database documentation. | 35 |

1. Commit all your code to a **GitHub repository**
2. Submit your GitHub repository URL through the **Classes** page on your school's official portal
3. Keep your repository well-documented and organized throughout the semester
